# Lessons Learned — AlamiaTravelOS

## Lesson 1: Bind Mount Type Mismatch on VPS (2026-09-05)

### Problem
Deploying `docker-compose.prod.yml` via Portainer on a VPS failed with:
```
failed to create shim task: OCI runtime create failed: runc create failed:
unable to start container process: error during container init:
error mounting "/data/compose/67/config/odoo.conf" to rootfs at "/etc/odoo/odoo.conf":
mount src=/data/compose/67/config/odoo.conf, dst=/etc/odoo/odoo.conf,
flags=MS_BIND|MS_REC: not a directory: Are you trying to mount a directory onto a file (or vice-versa)?
```

### Root Cause
Relative host paths (`./config/odoo.conf`, `./custom_addons`, `./third_party_addons`) in the compose file resolve against the VPS filesystem where the compose file is deployed. When Portainer stores the stack, relative paths resolve to Portainer's internal layout (e.g., `/data/compose/67/`). The target directory didn't exist, or the source path resolved to a file that Docker tried to mount as a directory.

### Solution
Switched to **named volumes** in `docker-compose.prod.yml`:
```yaml
# Before (broken on VPS)
volumes:
  - ./config/odoo.conf:/etc/odoo/odoo.conf:ro
  - ./custom_addons:/mnt/extra-addons

# After (fixed for VPS)
volumes:
  - odoo-config:/etc/odoo/odoo.conf:ro
  - custom-addons:/mnt/extra-addons
```

### Key Takeaways
1. **Never use relative bind mounts in production compose files** — they resolve differently on every host
2. **Portainer's compose storage path** (`/data/compose/<id>/`) is not under the user's control; don't assume directory hierarchy
3. **Named volumes are the production-safe pattern** — Docker manages creation, location, and lifecycle
4. **Environment variables with defaults** (`${VAR:-default}`) keep compose files portable across environments
5. **Always verify compose file locally** (`docker compose config`) before deploying to VPS

### Prevention Checklist
- [ ] All volume references use named volumes (Docker-managed) for production
- [ ] No relative paths in production compose volume sections
- [ ] `docker compose config` passes validation locally before deployment
- [ ] Environment variables documented in README or stack settings in Portainer
- [ ] Named volumes defined in bottom section with consistent naming (`odoo-config`, `custom-addons`, etc.)

## Lesson 2: PowerShell vs Bash Syntax (2026-09-05)

### Problem
Multiple git commands failed because `&&` (and `||`) operators are not supported in Windows PowerShell 5.1 as command separators.

### Root Cause
PowerShell uses `;` for command sequencing and reserves `&&`/`||` for newer PS 7+ versions only. The terminal environment here is PowerShell 5.1.

### Solution
Use `;` instead, or separate commands:
```powershell
# Instead of: git add . && git commit -m "msg"
git add file
git commit -m "msg"
```

### Key Takeaways
- When executing bash-style commands on Windows in this environment, chain with `;` or run sequentially
- Git commands that failed repeatedly need to be split into separate tool calls
- Verify exit status with `$?` when chaining with `if`
