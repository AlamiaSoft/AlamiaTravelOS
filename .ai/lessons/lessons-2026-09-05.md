# Lessons Learned — AlamiaTravelOS

## Lesson 1: Bind Mount Type Mismatch on VPS (2026-09-05)

### Problem
Deploying `docker-compose.prod.yml` via Portainer on a VPS failed with:
```
failed to create shim task: OCI runtime create failed: runc create failed:
unable to start container process: error during container init:
error mounting "/data/compose/67/config/odoo.conf" to rootfs at "/etc/odoo/odoo.conf":
mount src=/data/compose/67/config/odoo.conf, dst=/etc/odoo/odoo.conf,
flags=MS_BIND|MS_REC: not a directory: Are you trying to mount a directory onto a file (or vice-versa)?
```

### Root Cause
Relative host paths (`./config/odoo.conf`, `./custom_addons`, `./third_party_addons`) in the compose file resolve against the VPS filesystem where the compose file is deployed. When Portainer stores the stack, relative paths resolve to Portainer's internal layout (e.g., `/data/compose/67/`). The target directory didn't exist, or the source path resolved to a file that Docker tried to mount as a directory.

### Solution
Switched to **named volumes** in `docker-compose.prod.yml`:
```yaml
# Before (broken on VPS)
volumes:
  - ./config/odoo.conf:/etc/odoo/odoo.conf:ro
  - ./custom_addons:/mnt/extra-addons

# After (fixed for VPS)
volumes:
  - odoo-config:/etc/odoo/odoo.conf:ro
  - custom-addons:/mnt/extra-addons
```

### Key Takeaways
1. **Never use relative bind mounts in production compose files** — they resolve differently on every host
2. **Portainer's compose storage path** (`/data/compose/<id>/`) is not under the user's control; don't assume directory hierarchy
3. **Named volumes are the production-safe pattern** — Docker manages creation, location, and lifecycle
4. **Environment variables with defaults** (`${VAR:-default}`) keep compose files portable across environments
5. **Always verify compose file locally** (`docker compose config`) before deploying to VPS

## Lesson 2: PowerShell vs Bash Syntax (2026-09-05)

### Problem
Multiple git commands failed because `&&` (and `||`) operators are not supported in Windows PowerShell 5.1 as command separators.

### Root Cause
PowerShell uses `;` for command sequencing and reserves `&&`/`||` for newer PS 7+ versions only. The terminal environment here is PowerShell 5.1.

### Solution
Use `;` instead, or separate commands:
```powershell
# Instead of: git add . && git commit -m "msg"
git add file
git commit -m "msg"
```

### Key Takeaways
- When executing bash-style commands on Windows in this environment, chain with `;` or run sequentially
- Git commands that failed repeatedly need to be split into separate tool calls

## Lesson 3: Postgres Healthcheck Targets System Database on Container Boot (2026-09-05)

### Problem
Portainer stack deployment failed with `dependency failed to start: container alamiatravelos_db_prod is unhealthy`.

### Root Cause
1. `docker-compose.prod.yml` lacked `environment` definitions under the `db` service (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`), so Postgres initialized with standard defaults or failed authentication.
2. The `healthcheck` command tested `pg_isready -U odoo -d alamiatravelos`. When Postgres boots for the first time, database `alamiatravelos` does not exist yet (Odoo creates it later). `pg_isready` returned non-zero 5 times in a row, marking the database container unhealthy and preventing the web container from starting (`depends_on: condition: service_healthy`).

### Solution
1. Explicitly pass `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` environment variables to `db`.
2. Target system database `-d ${DB_NAME:-postgres}` in `pg_isready`:
```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U ${DB_USER:-odoo} -d ${DB_NAME:-postgres}"]
```

### Key Takeaways
- Container health checks must verify service readiness (is postgres accepting connections?), not business data existence.
- Always test against system default databases (`postgres`) in Docker health checks.

## Lesson 4: Odoo 19 Asset Bundle Cache Invalidation (2026-09-05)

### Problem
Clicking the Travel OS menu resulted in `KeyNotFoundError: Cannot find key "travel_dashboard_client_action" in the "actions" registry`.

### Root Cause
Even after upgrading `alamia_travel_reporting`, Odoo 19 served pre-compiled JS asset bundles cached in `ir.attachment` records (`/web/assets/...`). The new OWL client action code had not been compiled into the active minified asset bundle.

### Solution
Invalidated the asset bundle cache by clearing `ir.attachment` records matching `/web/assets/` via python script:
```python
env['ir.attachment'].sudo().search([('url', 'like', '/web/assets/')]).unlink()
env.registry.clear_cache('assets')
```
And updated the OWL Component definition to include `static props = ["*"]` and root `<templates id="template">`.

### Key Takeaways
- Modifying JS/QWeb assets in custom modules requires invalidating `ir.attachment` asset bundles or starting Odoo with `--dev=assets`.

## Lesson 5: Financial Audit Trail Write-Guard Pattern (2026-09-05)

### Problem
Financial figures on travel sales could be mutated silently after sale confirmation without audit records.

### Root Cause
Sub-lines (`travel.sale.line`) did not have `mail.thread` enabled and lacked write restriction logic.

### Solution
1. Inherited `mail.thread` on `travel.sale.line` with `tracking=True` on `unit_price`, `cost_amount`, `quantity`, and `supplier_id`.
2. Implemented `write()` override to block financial mutations on completed or cancelled sales:
```python
def write(self, vals):
    financial_fields = {'unit_price', 'cost_amount', 'quantity', 'selling_amount', 'supplier_id', 'service_id'}
    if financial_fields & set(vals.keys()):
        for line in self:
            if line.sale_id.state in ('completed', 'cancelled'):
                raise UserError(_("Financial fields cannot be modified on completed/cancelled sales."))
    return super().write(vals)
```

### Key Takeaways
- Server-side ORM guards (`write()` constraints) guarantee audit compliance even if UI buttons are bypassed via API/RPC.

## Lesson 6: Gitignore Wildcard Data Directory Rule (2026-09-05)

### Problem
VPS module installation failed with `FileNotFoundError: No such file or directory: '/mnt/extra-addons/alamia_travel_core/data/users_data.xml'`.

### Root Cause
`.gitignore` contained `data/` without a leading slash `/data/`. Git interpreted `data/` as a recursive wildcard matching all directories named `data` anywhere in the project tree, silently ignoring `custom_addons/alamia_travel_core/data/users_data.xml`.

### Solution
Updated `.gitignore` to use explicit root-level path `/data/` instead of unrooted `data/`.

### Key Takeaways
- Always use root-anchored slashes (`/data/`, `/logs/`) in `.gitignore` for persistent storage directories to avoid ignoring Odoo module `data/` folders.

## Lesson 7: Account Fallback for Invoice & Bill Creation (2026-09-05)

### Problem
Clicking **Create Invoice** threw `UserError: Please define an Income Account for service: Appointment`.

### Root Cause
Hard code assertion expected `line.service_id.income_account_id` to be explicitly selected on every catalog record.

### Solution
Added automatic fallback to default Chart of Accounts income and expense accounts:
```python
income_account = line.service_id.income_account_id or self.env['account.account'].search([('account_type', 'in', ['income', 'income_other'])], limit=1)
expense_account = line.service_id.expense_account_id or self.env['account.account'].search([('account_type', 'in', ['expense', 'expense_direct_cost'])], limit=1)
```

### Key Takeaways
- Always implement defensive fallback lookup to standard accounting accounts before throwing user errors on invoice generation.
